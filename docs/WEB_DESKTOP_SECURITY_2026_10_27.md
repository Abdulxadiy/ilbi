# Web/desktop presentation and support security review — 2026-10-27

Status: **TESTED_CODE**. No platform version bump, deployment or native package publication is claimed by this checkpoint.

The owner's observed SHA-256 on Downloads is a **public package checksum, not a password or password hash**. Ordinary Windows/Linux/Android cards no longer show it. Version/build/platform/size/download controls remain, and the release manifest and desktop installer's byte/hash verification remain intact. The short pairing comparison code remains visible because a user must compare it on both computers.

The wider source review found additional issues independent of that download display:

- Support customer profiles displayed the internal guest credential verifier. The row was removed even when an older server includes it. Backend removal is a separate coordinated server change.
- Support profile editing could send account role, email/recovery identity and account/store activity changes through the ordinary support endpoint. The UI now submits only `first_name`, `last_name`, `contact_phone`, `tenant_name` and `tenant_address`. Email/login phone/role stay read-only. Account security actions open the existing protected Accounts flow; store activity actions open Stores. Backend rejection/authorization/session-version tests are recorded by the backend security checkpoint, not inferred from hiding controls.
- Profile password-change modal values and reveal-toggle states survived closing. Opening/closing now clears all password fields and restores masked inputs. An explicit reveal click still works within that open dialog.
- Error-boundary rendering displayed raw exception text, and the API helper could stringify arbitrary error payloads into visible errors. Recovery now shows safe guidance. API errors, local toasts, audit descriptions and nested audit changes redact sensitive values. Historical `key`/`field`/`label` credential rows hide their `value`, `old`/`new`, `before`/`after` and `old_value`/`new_value` payloads. Server errors do not reveal debug bodies. Public artifact/certificate digests in explicit audit metadata, 64-character financial retry IDs and ordinary financial values/IDs are preserved.
- API field errors also pass through the presentation boundary. Credential metadata keys are excluded, hashes/tokens are masked, and a malformed response echoing the actual entered password is masked at the specific field. Normal password guidance, actual red highlighting and business `code`/`message` fields remain supported.
- Error responses are additionally scrubbed against sensitive values from that request's JSON body before an `Error`, its stack or its `.data` are created. This covers an unlabelled response such as “Rejected ‹the submitted password›” in a general banner or nested field, including refresh/ticket/OTP errors. The request-scoped path is never applied to successful token responses or ordinary business/chat content.
- Desktop IPC failures, updater status, helper failures and native error dialogs use safe messages. The main process sanitizes errors before they cross the sandbox boundary; sandbox/context isolation and successful bridge capabilities are unchanged. The native sanitizer is included in packaging inputs.

Support profile loading/saving now also guards the active conversation: late loads do not replace the new customer's form, and old save responses cannot update a different conversation's displayed profile.
