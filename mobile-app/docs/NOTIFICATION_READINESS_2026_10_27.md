# Notification readiness — 2026-10-27

The owner has now authorized notification implementation as part of production readiness. The earlier discussion-only boundary is superseded by this request. No production push/message is authorized as an incidental test.

## Verified inbox slice

The permanently disabled home bell and artificial red dot are replaced by a reusable bell backed by the actual recipient/tenant-scoped `/sales/notifications/` API. A dedicated sidebar/tab-preserving inbox supports server unread counts, cursor history, read/read-all, confirmed delete/clear, refresh, visible transport errors, and safe internal destinations. It never follows arbitrary notification URLs or returned pagination links. Report, debt and stock alerts open only permitted modules; supported sale links use an authorized receipt read. Unsupported B2B-only destinations remain readable notifications, without inventing mobile accounting actions.

`NotificationsProvider` scopes visible state to server/account/store, hides the previous store immediately, aborts old reads and ignores late responses, serializes list requests/actions, respects server Retry-After, and stops polling in background. The unread count is the server total, not the number of unread rows on the visible page. Read/delete state changes only after server acknowledgement. An ordinary notification arrival does not mark it read.

Authorized `tenants.manage_settings` users can change existing shared Z-report and low-stock inbox settings. These patch only `notify_web_reports` or `notify_web_low_stock` in `/tenants/current/`; they do not overwrite Telegram destinations or other settings. These are shared server inbox preferences, not OS push permission.

Actual final client checks: **28 focused tests / five suites passed**; strict ESLint passed for notification and shared navigation files; whole-app TypeScript and SDK/signing preflight passed. The Android Hermes export completed successfully with the new native notification dependency. Tests cover endpoint shapes, authoritative unread count, hostile pagination/target URLs, foreign recipient rejection, failed read/read-all acknowledgement, store-switch late-response suppression, destructive confirmation isolation, signed-out suppression, explicit OS consent/denial, rotation, stale-account/store taps, offline/late-registration revocation and unchanged-profile refreshes. A failed category change preserves the acknowledged setting; disabled server delivery and pending offline revocation are displayed explicitly. These are source/API-contract tests with isolated mock transport, not native push delivery or production-account tests.

## Direct FCM foundation — implemented and checked

`expo-notifications ~58.1.6` was installed using Expo's SDK-compatible installer. Native setup uses direct FCM, without requiring an additional Expo Push/EAS project solely for message routing. The owner provided a Firebase Android client for package `uz.ilbi.mobile`, project `ilbi-80eb1`, and a protected matching server service account. Only the public client configuration belongs in the APK. The private sender key remains outside Git and APK copying.

The client asks for permission only after an explicit enable action in inbox settings. It creates the Android channel, registers the native FCM token, refreshes binding on foreground/token rotation without token-listener recursion, and handles ordinary/initial notification taps. Foreground arrival refreshes the inbox without adding a floating overlay. Wrong-account payloads are discarded; another-store taps open store selection before reading protected detail. The server detail GET repeats recipient/tenant authorization.

Installation identity and its 256-bit revocation secret stay in SecureStore; no native FCM token is persisted by the JavaScript layer. Registration is authenticated at `POST /auth/push/installations/`, binds the request's actual user, encrypts the provider token at rest, stores the account token version and returns no token/secret. Revoke is a secret-only deactivate operation at `POST /auth/push/revoke/`, so cleanup can retry after local JWT clearing. Logout persists pending revocation first, drains an in-flight registration before deactivation, permits prompt local logout, and retries failed cleanup on startup. An already submitted generic notification can still race an offline logout; no private message/amount is included in the payload and taps always reauthorize.

The `apps.notifications` backend slice writes a unique durable `PushEvent` with each existing inbox notification. `Notification.save` is atomic so even autocommit scheduled producers cannot leave an inbox record without its outbox row. Delivery never retries a sale/report/transfer action. A per-event/installation unique delivery record and row locks serialize dispatch; Android notification tags coalesce a retried provider delivery. This is at-least-once transport, not a claim of exactly-once OS presentation.

The periodic worker checks live account/token version, active membership/store, category, read state, binding identity and event age before sending. Token rotation, removed memberships, reassigned installations, read/deleted notifications and invalid/unregistered provider tokens are handled. Transient errors persist bounded backoff; provider rejection is stored as a sanitized code. Expired-event backlog does not block current events. The five current delivery categories are B2B, debts, stock, reports and system; this transports existing notification producers, not every proposed event in the platform catalogue.

Push freshness and device eligibility use `PushEvent.created_at`, the real server-arrival time. A backdated business timestamp preserved by offline synchronization must not discard a newly committed inbox event. The specific regression is checked separately below.

**Backend verification after the arrival-clock correction: 19 push ORM/API cases plus three existing notification API cases passed on isolated PostgreSQL (22 total).** The regression confirms a newly arrived event is delivered even when its preserved business timestamp is three days old; expired outbox events still cannot delay a current event. A clean environment created with `uv sync --locked --group dev` imports the repository's frozen **Django 6.1.2**; the earlier minimum-version assumption of 6.0.7 was corrected. Ruff passed for all new backend notification files and the atomic notification model change. The notification migrations have no pending model changes. A global migration check briefly reported another agent's in-progress inventory model; that was not described as a notification failure or silently changed here.

The genuine service-account OAuth exchange succeeded without printing the access token or credentials. An explicitly authorized FCM `validate_only: true` request targeted a clearly synthetic, non-device token; the response was HTTP 400 / `INVALID_ARGUMENT`, reaching provider token validation rather than returning an authentication/API-disabled response. This is evidence of the credential/API validation path, **not a successful real send, device registration or OS delivery**. No real device/person was targeted.

## Server activation and remaining acceptance

The backend sender defaults to disabled. Configure the backend/worker with `FCM_PROJECT_ID=ilbi-80eb1`, `FCM_SERVICE_ACCOUNT_FILE` pointing to a protected mounted sender JSON, and `MOBILE_PUSH_ENABLED=False` until deployment checks are complete. Migrate `notifications` before routing traffic to code that writes outbox rows; run the new Celery worker/beat task. Backend and worker must use the same stable Django secret for encrypted tokens. Registration reports `delivery_enabled: false` while the sender is not enabled/configured; the app then explains that server sending is pending instead of claiming delivery is active.

This slice did not deploy or enable the sender on the production server. A rebuilt, signed Android package and an expressly authorized isolated native installation are still needed to verify native FCM registration, foreground/background/ordinary-closed behavior, tap, OS permission deny/re-enable, mute, logout and actual event delivery. iOS APNs credentials/build/delivery remain separate. No emulator command or modification of the owner's existing app was used here.

The broader catalogue remains work: support/chat, workspace tasks, security and other domain-only events require their own recipient-safe producers and acceptance; quiet hours/digests and domain-specific obsolete-event cancellation are not claimed complete by this foundation. Inbox read/delete cancellation and the 24-hour push expiry are implemented. Do not mark the whole platform notification audit complete from these checks.
