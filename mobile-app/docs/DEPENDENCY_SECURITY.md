## Focused Zod investigation — 2026-10-27

**No compatible upstream fix was found. This finding remains open.** Live npm metadata returned Zod 3.25.76 as the latest matching `^3.25.76`, Zod 4.6.7 as latest overall, Expo 58.0.19 and CLI 58.1.15. The [current Expo CLI manifest](https://github.com/expo/expo/blob/main/packages/@expo/cli/package.json) still requires `zod: ^3.25.76`. These match the installed locked Expo/CLI versions; reinstalling the same compatible range cannot remove the finding.

The problem is reproducible through the installed **V3 root entry point**, despite the published fix targeting V4. V3 checks an upper bound but marks the parse dirty and continues visiting every element. Safe bounded reproductions used only 1,000 invalid elements: `.array(z.string()).max(2)`, array `.length(2)`, set `.max(2)` and asynchronous array parsing each returned **1,001 issues**, starting with `too_big`. No OOM or large payload was attempted. [Upstream V3 issue #6653](https://github.com/colinhacks/zod/issues/6653) describes the same behavior; the maintainer stated on October 12 that new V3 versions are no longer published. Thus the finding cannot be dismissed as affecting only V4 or as a scanner false positive.

The [V4 change #6652](https://github.com/colinhacks/zod/pull/6652) rejects oversized bounded collections before walking elements; it explicitly leaves unbounded containers unchanged. A [contributor V3 backport](https://github.com/dokson/zod/commit/9f5b6c52) proposes three small upper-bound early-return changes for arrays/sets. It was inspected as a candidate, **not applied, accepted as an upstream release, or verified as a complete ILBI mitigation**. A vendor patch would need pinned input hashes, both CJS/ESM entry points and source consistency, sync/async and refinement/error-shape tests, plus tests at actual consuming boundaries. It must retain the real version and audit finding until the advisory/tooling recognizes the reviewed fix.

Direct CLI `require('zod')` usage was traced to DevTools plugin descriptor/output schemas and dynamically generated MCP command schemas. Plugin descriptors originate from autolinked installed packages; output comes from local plugin child processes/MCP extension results. The descriptor/output arrays have **no upper bounds**, and generated MCP argument schemas use primitive/enum fields. Consequently the constrained-collection backport alone would not bound these actual CLI arrays. A meaningful consumer mitigation would also require deliberate descriptor/output limits before parsing, including output-byte limits; compatibility and acceptable limits have not been established. No corresponding public ILBI production API or mobile application runtime import was found in this inspection. This is a scoped source finding, not proof of universal unreachability or native release acceptance.

The fresh **unfiltered** `npm audit --json` still reports three high entries / one underlying advisory and exits nonzero. No audit suppression, forced major override, dependency downgrade, package relabeling or APK/build-source mutation was made.
