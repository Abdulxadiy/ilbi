# Store settings readiness — 2026-10-27

Status: **TESTED_CODE**, awaiting server publication and installed-device acceptance. The settings forms and subsequent receipt snapshot/layout checkpoint are both implemented. This document does not claim that the original desktop parity audit is fully closed.

## Implemented

The dedicated authorized store-settings screen reads the current tenant's actual values and exposes six sections: store/receipt text, receipt paper/display options, tax configuration, manual/CBU currency, Telegram/inbox preferences and scheduled reports. Missing server fields stay unavailable instead of becoming defaults. Account/server/tenant guards reject stale responses. The existing general settings/theme/profile/version screen remains intact.

Only changed fields in the selected section are patched. Saving a schedule preserves unsaved receipt edits. A failed reload preserves the draft. User and backend validation errors identify the individual red input. Manual rates remain stored when switching to CBU; unavailable official rates cannot be silently invented. The conversion helper uses integer arithmetic and the actual six-place official rate and does not create financial transactions.

The server now returns an opaque `settings_revision`. Optional `If-Match` is checked while holding the existing tenant row lock. A stale revision returns HTTP 412 before saving or auditing. Legacy web/desktop callers without the header retain their existing API contract. The mobile client re-reads current settings, detects conflicts in explicitly edited fields, then sends the fresh revision to close the read/patch race. A response lost after applying a patch can be read back without repeating the mutation. Low-stock weekday/day and Telegram destination validation now reject values that previously could create unusable schedules/destinations.

The receipt settings include a clearly labelled new-receipt preview using the existing integer tax helper. Historical receipts/PDFs use the saved `sale.receipt_snapshot` for name, address, phone, header/footer, registered seller identity, paper width and cashier/customer/item-tax visibility. They never request today's tenant settings. The old renderer multiplied quantity by unit price, which omitted tax added above the price; the new renderer displays the server's saved item `total_price`. Missing historical line totals are shown as unavailable instead of being recalculated. All document text is escaped before HTML export. Print/PDF options use the selected saved 58/80 mm width; native printer/PDF acceptance remains separate.

Telegram test/daily/low-stock report actions require a separate explicit confirmation and use the saved configuration. Loading or saving settings never sends a message. Unknown delivery results are not retried automatically; the user first reviews Telegram before another request. **No real Telegram message or report was sent during implementation.** Delivery tests intercept only the external transport/task boundary; ORM, authorization and configuration transactions are real.

## Actual verification

- **40 mobile tests passed across three suites**: 27 settings model/command/rendered-form tests and 13 receipt tests. They cover exact section patch/revision, concurrent edits, lost-response read-back, old server, account/permission isolation, exact conversions, invalid rates/tax/schedules/destinations, red backend fields, preserved drafts, reload failure, explicit send confirmation/unknown-result blocking, historical identity/privacy, escaped PDF text, authoritative VAT-inclusive line totals and 58/80 mm export options.
- **73 real Django/PostgreSQL tests passed**, including the new mobile settings suite and existing receipt, currency, settings permissions/audit and service API suites. Coverage includes concurrent same-revision one-winner behavior, tenant binding, no-op revision, delegated permissions/revocation, invalid schedule fields and immutable old receipt snapshots after an actual settings API patch.
- Whole-mobile typecheck and strict scoped lint passed. Evidence: [mobile tests](evidence/store-settings-2026-10-27/mobile-tests.txt), [backend tests](evidence/store-settings-2026-10-27/backend-tests.txt), [typecheck](evidence/store-settings-2026-10-27/typecheck.txt), [lint](evidence/store-settings-2026-10-27/lint.txt).
- **Real Chrome UI regression passed** against a separate source copy, Metro process and browser profile using explicitly synthetic preview APIs: navigated through the real settings entry, persisted separate receipt/schedule sections, showed an invalid weekday in red, read back an actual CBU fixture and exact conversion, then opened an older saved receipt and verified its footer remained unchanged. Script: `tests/storeSettings.browser.mjs`. Evidence: [browser result](evidence/store-settings-2026-10-27/browser.txt), [red schedule field](evidence/store-settings-2026-10-27/schedule-invalid.png), [CBU conversion](evidence/store-settings-2026-10-27/currency-cbu.png), [saved receipt](evidence/store-settings-2026-10-27/saved-receipt-snapshot.png). These fixtures do not prove live backend delivery or native PDF generation.

An initial backend run failed two test fixtures: the second owned store lacked its required owner membership, and the snapshot sale test did not explicitly enable the local non-fiscal sandbox. Both fixtures were corrected; the production retail fiscal guard remains unchanged. An initial form effect triggered React compiler lint; loading was moved to a cancellable asynchronous callback before the passing checks. The first browser run completed the settings flow and reached the receipt, then its assertion tried to serialize a DOM element; the test was corrected to return a boolean before the passing rerun. No failed run is counted as acceptance evidence.
