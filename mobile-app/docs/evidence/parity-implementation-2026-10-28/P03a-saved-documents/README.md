# P03a — authoritative mobile receipts and A4 documents

Implemented → tested → failures resolved → evidence recorded. This is source/controlled-renderer verification, not completed P03 or native production acceptance.

Three retained red regressions in `before-freshness.txt` reproduce the old behavior: an in-memory receipt skipped the detail GET entirely, export used an earlier balance after a return, and an offline recheck did not block an old PDF. The receipt screen now fetches and validates the selected scoped detail on focus, invalidation and each print/PDF/share/link action. Old list/cache snapshots cannot authorize an export. Wrong IDs, invalid money/date/status/currency, duplicate/missing rows, inconsistent original row totals and return/net totals are blocked with retry. Account/store/server generation, focus epochs and request ordering prevent a late lookup/file result entering another document. Concurrent actions are disabled; late invalidation rejects an outdated export acknowledgement. No financial mutation is added.

The Hujjatlar list has a permission-guarded A4 entry; the receipt view can switch between thermal and A4. Both exports use one curated saved-sale model, the approved monochrome SVG logo, stored receipt identity/layout flags, original product/variant/SKU/barcode/MXIK/package identifiers, authoritative line VAT/gross totals, original quantity and returned quantity. Original total, refunded amount and net remainder stay separate. UZS/USD are explicit, formatting preserves cents, dates explicitly use Asia/Tashkent. Unknown old metadata and unprovided cash-received/change are shown as unknown; they are not multiplied, converted or reconstructed. A4 cash/card/debt/partner/B2B titles reflect the actual transaction; an unsigned copy is explicitly unsigned and nonfiscal.

Sharing now verifies and generates a new PDF directly. The PDF preparation action says `PDF tayyorlash`, and the result says temporary file; a native chooser does not prove permanent saving or physical printing. Link copying also rechecks the transaction and keeps bearer receipt tokens on their API origin, removing the old hardcoded production-origin assumption. Relative/unverified origins, invalid tokens and preview records cannot produce a link. Custom deployment public-route availability is still an acceptance check.

## Remaining acceptance and next slice

DMP-065 is `TESTED_CODE`, not ACCEPTED. DMP-066/067 signatures/signed PDF, DMP-070 QR/barcode, DMP-071 rotate/revoke and DMP-072 real save/open still need their own implementations and acceptance.58/80mm device pagination/printer/font/long-receipt behavior remains open. The backend preserves legacy pre-product-snapshot display by using current catalog names/codes with unknown fiscal identifiers; old cashier/customer names also come from related current records. Do not claim these are fully frozen historical identities or backfill missing history from today's data. Preserve this limitation until the subsequent identity work defines/labels it.

Android/iOS file lifecycle, chooser cancellation/error, user-visible save/reopen after restart, physical printing/scanning, signature persistence/server-sync policy, production deployment, upgrades and the existing dependency-security/fiscal/provider gates remain open. Existing emulator/app/data, published build5, versions, web/desktop login and production server are untouched. The master plan remains; cleanup is forbidden while these requirements remain.

Matching SDK58 references read before native API work:[Expo Print](https://docs.expo.dev/versions/v58.0.0/sdk/print/) documents that `printToFileAsync` creates a cache file and web opens a print dialog; Android print-window resolution does not certify completed printing.[Expo Router](https://docs.expo.dev/versions/v58.0.0/sdk/router/) supplies the focus lifecycle used here.
